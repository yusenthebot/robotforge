# robotforge

robotforge is a robot playground on the MuJoCo physics engine, made for beginners.
The user describes a robot and a goal in plain words; you build it with the robotforge MCP tools, make it move, check the result and explain the idea behind each step.
The tools come from the `robotforge` MCP server: Claude Code names them `mcp__plugin_robotforge_robotforge__<tool>`, Codex `mcp__robotforge__<tool>`; search your tool list for `robotforge`.
Clients that load MCP tools on demand (recent Codex) show them only through their tool search: search it for `robotforge` before deciding they are missing.
The very first start installs the server's Python packages and can take a minute, so if the tools are not there yet, wait and look again before anything else.
Do not work around missing tools by importing robotforge's Python modules yourself: nothing would show in the user's viewer. Follow [references/troubleshooting.md](references/troubleshooting.md) instead.

## Workflow

1. **Understand the wish.** If the request is clear, act with sensible defaults. Ask one short question only when a choice really matters (which robot, what it should do). "Teach me" or "lesson N" means the learning path: call `lessons`.
2. **World.** `new_world(name, floor)` creates a project; `open_world` reopens one.
   - Ready-made scenes (`list_scenes`, `load_scene(preset)`): desk_lab, kitchen, home (a kitchen and a living room with a swing door, for a dog with an arm), factory, warehouse, park, maze, obstacle_course, and with water harbor, lake, pool. Robots already in the world move to the scene's places (boats and ROVs onto the water).
   - A world from a sentence: `load_scene(description="a small flat with a kitchen, a living room and a bedroom, two red cups", seed=0)` lays out rooms with doorways and furniture (each room's floor is a marker named after it, so `move(robot, to="kitchen")` works), a warehouse (racks, pallets, a packing table with a tote, a loading dock) or an outdoor place (hills, rough ground, stairs, ramps, stepping stones, trees, rocks); the things it names go on tops an arm reaches from floor the robot gets to. `scene.generated` lists what it understood and the things to pick up; another `seed` is another layout.
   - Tasks: `add_task("bring the red cup from the kitchen to the bedroom desk")` saves a goal with the world (go to, bring, put, pick up, push, open, close, press, switch on, in English or Chinese), finds the thing and the place by name, kind, color and room, and adds what is missing (the thing, a bin, a lift_picker for fetching, a template arm beside a drawer). Do the task with the usual tools (`pick_and_place`, `move`, `operate`), then `observe`: its `tasks` field says `done` and the `distance_m` still to go; only `done: true` counts. `remove("task_name")` deletes one.
   - Ground and terrain: `set_floor(style)` (checker, grass, wood, concrete, dirt, sand, rock, snow, tile); `set_terrain(type)` for the whole ground or `add_terrain(type, pos)` for one feature (hills, rough, stairs, ramp, stones, curb, platform).
   - Water: `set_floor(water=1.2)` fills the world 1.2 m deep (or `water={"level": 1.2, "waves": 0.03}`); higher terrain is dry land. Light things float, heavy ones sink; `add_object(shape="buoy")` is a moored buoy, `shape="dock"` a wooden dock.
3. **Robot.** Pick the source that fits:
   - template (`list_templates`): arm, quadruped, humanoid, rover, cartpole, boat, rov (an underwater robot), drone (4, 6 or 8 rotors), tuned with `params` (sizes, servo, color);
   - library (`list_library`): real robots such as `go2`, `panda` or the `skydio_x2` and `crazyflie` drones, downloaded on first use (4-55 MB); `mounts` puts one on another, an arm on a dog's back (`add_robot(name="go2", library="go2", mounts=[{"library": "piper"}])`, then the arm is `go2/arm`, and a walking dog stops before it works) or a gripper on an arm's flange (`ur5e` with `robotiq_2f85`, also on a dog: `anymal_c` with both); each walker carries only what `list_library` says (`carries`);
   - open catalogue (`list_library(kind="arm", search="kinova")`): over 200 more open robots from many makers (arms, dogs, humanoids, wheeled bases, hands, drones), `add_robot(name, library=<name>)` downloads just that robot's folder once, runs it through the import doctor and answers with `catalogue`: what it is by its structure (arm, quadruped, humanoid, wheeled, hand, aircraft, other) and which tools fit (arms get a tool point and flange for `move_arm`; legged robots walk with `move` when a gait fits their legs, and `catalogue.checked` says what a short trial of the new robot showed (stands, walked or fell over after how far; the gait is generic, so read it before trusting `move`); the rest move with `set_controls` and `pose`); `kind` and `search` match whole words of the name, maker and tags (`gripper`, `dog`, `drone` work as kinds); a robot that did not load comes back with the doctor's reason;
   - file: `add_robot(file=...)` imports URDF, xacro, MJCF or a mesh and returns the import doctor's report;
   - parts (`builder_guide`, then `add_part` / `update_part` / `remove_part`): any robot from bodies, legs, wheels, rotors, arms, grippers and sensors (hexapods, snakes, self-balancers, an arm on a rover, a hexacopter);
   - design (`list_templates` lists them): a ready-made unusual robot from the gallery, `add_robot(name, design="centaur")` (wheel-legged biped, Mars rover, centaur, scorpion, a Go2 carrying a PiPER arm, tentacle...), saved as parts so `update_part` changes it;
   - a sentence: `add_robot(name, describe="a six-legged robot with two arms")` generates a new robot from parts (4 or 6 legs, 2/4/6 wheels, a snake, a standing arm, a self-balancer or a humanoid; 0-2 arms with gripper, suction or magnet; sizes, colors, materials, head, camera, lidar, cargo box) that walks, drives or reaches at once (the result's `generated.how` says with which tools); `params={"seed": 3}` is another variation, `update_robot(name, describe="make it longer")` changes it ("six legs instead of four", "add an arm", "another one");
   - nothing fits: write a small URDF and import it (see recipes).
   - combining: `mount(what, on)` puts anything on anything in one call, on an adapter plate: an arm on a base (`mount("ur5e", on="cart")`), an end effector on that arm's flange (`mount("robotiq_2f85", on="cart/arm")`, also `panda_hand` or the dexterous `leap_hand` and `allegro_hand`, whose fingers close together as the gripper; another one swaps it, a quick change), a sensor on its wrist (`mount("lidar", on="cart/arm")`); `at` names a body, `shift` and `rotate` place it. Read `checks`: `mass_kg`, `stands.margin_m` (how far the centre of mass is inside what it stands on), each arm's `reach_m`, `reaches_floor`, `self_collision`, `holds`, `tips_robot`. A robot that would tip or fall is refused with what to change. `save_as="name"` keeps the combination (a name already saved is refused unless `overwrite=true`, and a design cannot carry itself); `add_robot(design="name")` or `mount("name", on=...)` uses it again; `remove("cart/arm")` takes a mount off.
   Add props with `add_object` (box, sphere, cylinder, table, bin; `material="steel"` for what a magnet holds).
   Things that move on a joint of their own are objects too: drawer, cabinet (a door), button, switch, lever, valve, conveyor (`speed` in m/s), door (a room door in a `door_frame`: robots push it open walking or driving through, and it closes by itself), and soft ones: rope, cloth.
   - End effectors: any arm takes `end_effector="suction"` (a suction cup: flat things fingers cannot get round, a tile, a plate) or `"magnet"` (steel only: `material="steel"` things, and the steel bars of drawers and doors) in `add_robot`, or later in `update_robot` (a tool change; `"gripper"` goes back to its fingers). `gripper(robot, "close")` turns a cup or magnet on, `"open"` off; `pick_and_place` uses them as it uses fingers. `"wiper"` is a flat sponge pad for wiping and pressing (it holds nothing, so that arm cannot pick).
   Sensors go on any robot's body with `add_sensor` (camera rgb, depth, segmentation, `stereo` (depth from disparity), `fisheye` (up to 200 degrees) or `event` (brightness changes), 2D or 3D lidar, IMU, encoders, force_torque at a wrist, touch arrays on feet, rangefinder, GPS, odometry, `wheel_odometry` for a rover's wheels, `sonar` for a cone that is deaf up close, `skin` for taxels over faces of a body, `temperature` and `gas` that read `heat_source` and `gas_source` objects (`add_object(shape="heat_source", strength=80)`); rate, noise, latency in `options`); `read_sensors` reads them (`points=200` adds a depth camera's or lidar's point cloud in world coordinates), `remove("robot/sensor")` takes one off.
   Perception: `mapping(robot, "start")` makes a robot (a Go2, a rover, any mobile robot) draw an occupancy-grid map of where it goes from a lidar and an odometry (added if it has none), with a particle filter that keeps its pose estimate honest against the odometry's drift; `mapping(robot, "explore", options={"seconds": 120, "area": [x0, y0, x1, y1]})` has it go to the nearest unseen frontier again and again; `mapping(robot, "status")` gives the pose estimate with its `pose_error` and the `odometry_error` beside it, and the map's `accuracy` against the scene (`precision`, `wall_error_m`, `recall`, `explored`; `options={"image": true}` draws it); `"localize"` finds the robot in the finished map from where it believes it is (`init="pose"`) or from nowhere (`"global"`, it gathers as the robot moves); `"stop"` keeps the map without growing it, `"clear"` drops it. `move(robot, to=..., map="own")` goes by the robot's own map and pose alone and plans only through space it has seen free (explore first); the result's `on_its_own_map` says where it believed it was and how far off that was. A mapping started with `pose="truth"` or `"odometry"` steers by that and the result's `pose_source` says so; `localize` warns (`warning`) when the map has too few walls to match scans against. The viewer draws the map, the particles and the pose estimate beside the odometry's own, drifting one.
   The viewer draws what added sensors sense: lidar rays and points, a camera's picture beside the view, IMU, encoder and force plots, touch pads and force arrows; `open_viewer(show=["go2/front_cam"])` also draws one the robot came with and brings a camera's picture up.
4. **Viewer early.** Call `open_viewer()` as soon as a robot exists and tell the user what they can do: drag the robot, drive with W A S D or a gamepad (sticks jog an arm, A and B close and open its gripper), and use the panels.
   The top left "Maps, terrain, modes" panel switches scenes, ground and terrain, and how each robot is controlled (keyboard gait, learned walk, MPC, LQR, IK...); the Robots panel has the joint sliders; Learn opens hands-on lessons.
   While the viewer is open, actions play out in real time.
5. **Make it move**, with the highest-level tool that fits:
   - `move` / `stop` / `pose`: walk a quadruped or humanoid (Go2, A1, ANYmal C and Barkour take 8 cm stairs, slopes and gravel on their own and slow to 60 percent of top speed over rough ground; Spot stands before steeper stairs and `pose` says `blocked`; humanoids walk flat ground; check `upright` after crossing terrain; a humanoid from the catalogue or a file stands by whole-body balance, which holds a load and takes a small push, and `robots` says `balance`; `move` walks it only when a gait fits its legs), drive a rover or a boat, humanoid poses; a boat's `move(to="dock")` plans round buoys and the shore; an ROV's `move(to=[x, y, z])` dives to that point and holds depth and heading (z is height above the floor like every z, depth = water level - z: 0.5 m under a surface at 1.2 m is z = 0.7; the result's `depth_m` is the depth reached; a point on land or under the bottom gets `why` with the z range that works; its `depth` sensor reads meters under the surface);
   - aircraft (kind `aircraft` in `robots`): `move(robot, to=[x, y, z])` takes off and flies there, then hovers; a list of points flies a path, e.g. a 3 m square at 2 m: `to=[[3,0,2],[3,3,2],[0,3,2],[0,0,2]]`; a last point with z 0 lands there (one call can take off, fly the path and land); z is a height above the world's zero, not above the ground under it, so over a hill or a table check `clearance_m` in the result; a point under a tree's crown or a table hovers there (z at the table's height lands on it); a landing where something stands (a ball, a crate, a robot), on top of what moves or a crown, or at an edge is refused with a spot nearby on the same surface that has room; legs go over or round what is in the way; `stop` hovers in place; `simulate(seconds, wind=[x, y])` blows a gust to show how it holds its place; the viewer flies it with W and S (forward, back), A and D (sideways), the arrow keys (turn), E (up) and Q (down); dragged with the mouse it holds where it is let go; `compare_controllers(drone, task="hover", push_at=3)` compares its own flight controller (`cascade`: position, attitude, body rates) with `lqr` and `mpc`, and `run_controller` flies it with one of them until `stop`, which hands it back to the flight controller;
   - `move_arm` / `gripper` / `pick_and_place`: arms; with an arm on a robot that drives or walks (`mobile_panda`, `lift_picker`, `go2_arm`), `pick_and_place` fetches: the robot goes over, picks the thing up, carries it and puts it down ("bring the apple to the table"), and says what it did or why it cannot before it moves; `pick_and_place(robot, object, "drawer")` puts things in an open drawer; `pick_and_place(robot, object, target, hand_to="other_arm")` has two arms that stand apart hand it over (the first sets it down where both reach and goes aside, the second takes it to the target: `handed_over`); a box riding on a running conveyor is caught as it goes by, the belt left running (`caught`, `caught_at`; an arm beside the belt, or a mobile one that drives to a place beside it from which its arm reaches, `stood_at`, and then carries it; too late for that, it waits for the box at the end of the belt and fetches it as it lies). `plan_grasp(robot, object)` shows how the gripper can take hold of a thing from its shape (a T-block, bottle, stone or mesh: `tee`, `bottle` and `stone` are pickable shapes); `pick_and_place` takes the best of those grasps by itself for anything that is not a plain box, can or ball, and reports it as `grasp`.
   - `operate(robot, target, action, amount)`: an arm opens or closes a drawer (amount in m) or a cabinet door (degrees), presses a button, flips a switch or a lever, turns a valve (open, close or turn, degrees); it holds the handle and follows the joint's own line or arc. An arm on a robot that drives or walks (`go2/arm`) goes over by itself when the handle is out of reach, stands clear of what moves while it works and folds its arm back (the result adds `went`, `stood_at`, `visit_s`; `go=false` keeps it where it stands). Read `success` and `notes`: a note says when the arm could follow only part of the way (move the thing nearer) or did not take hold (move it a little and try again); `force=15` makes the hand push the handle with at most 15 N (0 to 1000, not with press) and say whether it stalled (`add_object(..., resist=60)` makes a drawer, lever or valve take 60 N at its handle).
   - a conveyor runs by itself: `set_controls({"<conveyor>/speed": 0})` stops it, any other value (m/s) runs it;
   - `run_controller` / `compare_controllers`: a named algorithm on a task (reach, press, wipe, balance, stand, walk, drive_to), see `list_algorithms`; an arm's tasks also take `joint_impedance`, `cartesian_impedance` and `osc` (compliant control that gives way to touch); `press` stops at a force or holds one and `wipe` slides a pad over the table at a constant pressure (`task_params={"force": 8}`; give the arm a wiper first); `compare_controllers(robot, task="wipe")` puts the methods side by side with the mean force, its spread and the path error; `insert` puts a peg the gripper holds into an `add_object(shape="socket")` hole the robot has wrong by a few mm (`task_params={"hole": "socket1", "error": [0.006, 0]}`; grasp the peg first with `move_arm` and `gripper`);
   - `set_controls` + `simulate`: raw actuator targets;
   - `write_script` + `run_script`: custom sequences, loops and logic the user can keep;
   - learned walkers: `list_walkers`, then `move(robot, speed, walker="rl")` walks with a policy trained by reinforcement learning (a Go2 walk ships with robotforge; `walker="gait"` goes back);
   - a robot that no gait code knows, built from parts or imported from a URDF or MJCF file (`move` says so), can learn a walk of its own in the viewer's RL II lesson ("Keep this walk for my robot") if position servos move its legs; `robots` then lists its `learned_walk` and `move` uses it: forward at its own pace (holding its heading and the line it started on once that is learned, `holds_heading`), and once its turns are learned (they follow keeping the walk) turning on the spot: `turn_deg_s` is the slower side's rate from standing, `turn_deg_s_from_walk` each side's average in a turn's first second when the turn follows 1.5 s or more of walking with no pause (viewer closed, or walking with `seconds=null` and then the turn) that did not start right out of a turn; single turns vary (most within a quarter of it, a few far off), so read `turned_deg` from `move` and correct;
   - an MJCF file whose legs have torque motors (most Menagerie quadrupeds) cannot learn one (`move` says why); the same robot from the library (`add_robot(library=...)`) walks with its gait;
   - when the user asks such a robot (it has a `walk_hint`) to walk, say so before anything else and offer that lesson: about ten seconds of learning, and the walk is kept; a hand-written gait script is the fallback if they decline;
   - `train_policy`: teach any robot a task by trial and error, in the background, with any algorithm: `algo=["ars", "cem"]` (numpy, nothing to install) or `ppo` / `sac` (optional `rl` extra) or a plugin's, several at once to compare them, `search={"trials": 9}` to tune their settings (successive halving); the observation includes what the robot's sensors read, so `add_sensor` first to give the learner a lidar or an IMU; `training_status` shows every trial side by side and the viewer's Training panel draws the curves and plays the best policy; quote `winner.held_out` from `training_status` (a search's own score flatters its winner), and give `reach` a target with a small `jitter` when using ars or cem (see `docs/TRAINING.md`); `unilab_check` / `unilab_train` for the UniLab backend.
   - a video to keep or share: `move(..., record=true)` or `run_script(name, record="show.gif")` saves the motion, playing in real time (record=true: a GIF; a file name picks `.gif` or `.webp`, and `.mp4` is saved as a GIF) in the world's `videos` folder; the result's `video.path` says where, to copy it from. No browser is needed.
6. **Check, then explain.** Verify with numbers and an image (next section), explain what happened and why, offer a next step.

## Conventions

- Names are lowercase with underscores: worlds, robots, objects, scripts.
- A robot's parts carry its name as a prefix: actuators, joints, sensors and cameras are `<robot>/<name>` (`dog/front_left_knee`, `rover/front_cam`). Read them from `describe_model` or the add_robot result; never guess.
- Units: meters, kilograms, seconds; joint angles in radians; yaw and heading in degrees, counter-clockwise from +x; speed in m/s; turn in rad/s, positive is left.
- `pos` is [x, y] on the floor (height is automatic) or [x, y, z] for objects. z is up; a robot at yaw 0 faces +x.
- A world is a folder, `~/robotforge/worlds/<name>/` (or under `$ROBOTFORGE_HOME`), with `world.yaml` and `behaviors/*.py`. `show_world` prints it; `undo` reverts the last edit.

## Check your own work

Never say something worked because the call returned. Read the numbers, and look at an image for anything visual.

| After | Check |
|---|---|
| `add_robot`, `add_object` | it is listed; `observe()` shows it where expected; for imports read `doctor` (fixed, unfixed, notes) |
| `move` | `distance_m`, `turned_deg`, `to.upright`, any `note` (why it fell short); with `seconds` it has stopped already (`stopped: true`, no `stop` needed) |
| `move` with `to`, an aircraft | `arrived`, `to.position` against the target, `max_tracking_error_m`; landing: `landed` and `touchdown_m_s` (below about 0.4 is gentle); `robots` shows its `flight.state` and `altitude_m` |
| `pose` | `upright`; `blocked` when a quadruped stands before ground too steep for it (Spot before 8 x 30 cm stairs) |
| `move_arm` | `tool_position` against the target (within about 3 cm) |
| `pick_and_place` | `success`, `object_position` |
| `operate` | `success`, `moved` (m or degrees), `state`, any `notes` (how far the arm could follow); `observe()` lists every mechanism under `mechanisms` |
| `run_controller` | `success`, `failed_at`, `reward`, `stopped_early`; `keeps_running` means call `stop(robot)` later |
| `compare_controllers` | the `table` and `best`; explain with its numbers |
| `run_script` | `ok`, `output`, traceback |
| `mapping` | `state`, `pose` and `pose_error` against `odometry_error`, `accuracy` (`precision`, `wall_error_m`, `explored`); explore says `ended` (`explored`, `out_of_time`, `stuck`, `blind`); `move(..., map="own")`: `arrived` and `on_its_own_map.error_position_m` |
| `demonstration` | `start` says what is kept (`sensors`); `stop` says `seconds`, `frames`, `command_counts` and the `path` (a recording that was cut short says why in `note`); `replay` says `done`, `commands_issued`, any `refused` command (out of reach for the other robot) and `speed_scale`; `export` gives the `path` |
| `add_sensor` | `sensor` name, `position_m`, the first `reading`; then `read_sensors` (lidar `ahead` and `nearest` with `bearing_deg`, depth `nearest` distance; `center_m` is depth along the axis) |
| `set_controls` + `simulate` | `observe()` joints against controls; any `warning` |

`observe(view=...)` takes default, front, back, left, right, top, a robot's name (`view="dog"`: the default view framed on that robot), or a robot camera such as `dog/front_cam`.
`observe(view, find="red")` (a color name, a hex code, or "all") lists what that view sees of the color: each find's world `position`, the `object` name `pick_and_place` takes, and `about_cm`, how far off the position may be.
A flag on a find (cut_off, hidden, side_on, raised, held_by) means it may be much further off; the result's `how` says what each one it carries means.
A lidar (a sensor on a robot built from parts) comes whole in `observe()`'s `lidars`: `nearest_m`, `nearest_bearing_deg` from the robot's front (positive is left), `nearest_side`, the nearest hit on each side, and every ray in `ranges_m` (null: nothing within range).
A lidar or rangefinder sees past its own robot's parts (a column, the wheels), so its nearest hit is something else.
Without OpenGL it returns the state with a note instead of an image: rely on the numbers and ask the user to look at the viewer.
When something fails, say so plainly, read the error (it says what to do), fix it and check again.
Report real numbers, including disappointing ones.

## Teaching

- Answer in the user's language. For Chinese users, give the English term once in parentheses (逆运动学 inverse kinematics).
- Before each step, one or two sentences: what you will do and the idea behind it. One new concept at a time, with a plain analogy.
- Invite the user to try things by hand (sliders, dragging, W A S D) and to change one number and see what happens.
- Write code the user can read, with comments. Keep messages short and end with a concrete next step.
- More in [references/teaching.md](references/teaching.md).

## Lessons

`lessons()` lists nine beginner lessons; `lessons(number)` returns one lesson's plan: ideas to teach, tool steps, checks and a closing challenge.
Follow the plan and adapt it to the learner. MCP clients with prompt support also list them as prompts `lesson_1` to `lesson_9`, plus `start`.

The viewer has its own hands-on lessons behind the Learn button (学习): PID control, inverse kinematics, motion planning, sensors, finding an object with a camera, gaits, balance and reinforcement learning (a cart-pole, then any body learning to walk, the user's own robot included), real-robot face-offs (our arm next to the AgileX PiPER and Franka Panda, our humanoid next to the Unitree G1), plus challenges with stars (maze escape, shove survival, obstacle course).
Each is a guided experiment with live plots, quizzes and checks that run on the physics, and it works without you.
When a beginner wants to understand how robots work, open the viewer and suggest one; afterwards, offer to build on it in their own world.

## Extending

The user's own code adds to robotforge: parts, sensors, controllers and behaviors, written as small Python plugins.
`write_script(name, code, plugin=true)` saves one as `plugins/<name>.py` of the open world and loads it at once; the result says what it added or the line where it failed.
A plugin part is a shape for `add_object`, a plugin sensor a type for `add_sensor` (its own options go in `options`), a controller runs inside the simulation and a behavior is a routine for any robot: `plugins(action="run", name=..., robot=..., options=..., seconds=...)` starts either, and `stop(robot)` ends a controller.
`plugins()` lists everything plugins added (each with its options) and every file that did not load, with why; `plugins(action="reload")` reads the folders again after an edit.
A world's plugin files that were not written on this computer do not load until the user has approved them (every file under plugins/, as one set): read them with `plugins(action="show", world=NAME)`, tell the user what they do, and if they want them they run `robotforge plugins trust WORLD` in a terminal; you cannot, they are Python that runs with the user's rights. A world that uses a part from them does not open until then.
`export_model()` writes the open world as MJCF for other simulators, `export_model(robot="go2")` one robot, `format="urdf"` a robot as URDF; meshes go beside it as OBJ files, and `check` in the result says the file was loaded again and matched.
`demonstration(action="start", robot=..., name=...)` records what a robot does (joint positions, actuator targets, base pose, sensor readings, and the commands it is given from the keyboard, a gamepad in the viewer, `move`, `move_arm` or a script); act, then `demonstration(action="stop")` saves it as `demonstrations/<name>.json` in the world; `action="replay"` plays it on the same robot or another of its kind (`mode="commands"`, the default, gives the recorded commands again; `mode="joints"` plays the actuator targets back on the same actuators); `action="export"` writes `format="json"` or `"npz"` for training (never over an existing file or another demonstration unless `overwrite=true`) (LeRobot's parquet needs a library robotforge does not install). Scripts: `robot.record(name)` and `robot.replay(name)`.
In scripts `sim.robot(name)` is one interface to any robot (`robot.sensors`, `robot.move`, `robot.arm`, `robot.gripper`, `robot.on_step`), so one script runs on a template dog and on a Go2.
`robotforge.flow` gives scripts behavior trees and state machines (`Tree(Sequence(Action(fn), Retry(Action(fn2), times=3))).run(sim, robot)`) and the viewer shows which node runs.
